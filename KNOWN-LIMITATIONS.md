# KNOWN LIMITATIONS — What Stakeholders Should Know Up Front

This document lists the limitations of the Register of Trade Unions that
stakeholders should be told BEFORE testing begins. These are not bugs —
they are conscious design decisions, deferred work, or environmental
dependencies. Knowing them up front prevents "I thought this was broken"
reports during testing.

**Last updated:** 2026-10-12 (Step 7).

---

## 1. Demo accounts use a known password

The three demo accounts (`registrar@example.com`, `inspector@example.com`,
`officer@example.com`) all use the password `Test!2345`. This is hardcoded
in `prisma/seed-demo.ts` for testing convenience.

**What this means for testing:** you can log in as any role immediately.
**What this means for production:** these accounts MUST be deleted or
given strong passwords before go-live. The seed script refuses to run in
production (`NODE_ENV=production`) for this reason.

---

## 2. The database is SQLite, not PostgreSQL

The system uses SQLite (`db/custom.db`) for development. This is fine for
testing and small deployments, but PostgreSQL is recommended for
production (concurrency, backups, replication).

**What this means for testing:** everything works. **What this means for
production:** a migration to PostgreSQL is needed before go-live. The
Prisma schema is database-agnostic — only the `provider` line in
`prisma/schema.prisma` needs to change.

---

## 3. PDF generation requires WeasyPrint (Python)

The compliance report PDF is generated by rendering HTML to PDF via
WeasyPrint (a Python library). If WeasyPrint is not installed on the
server, the "Generate Report" button will return a 500 error.

**What this means for testing:** PDF generation works in the dev
environment (WeasyPrint is installed). **What this means for production:**
the production server must have WeasyPrint installed
(`pip install weasyprint`). The `scripts/render-pdf.py` script is the
bridge between the Next.js app and WeasyPrint.

---

## 4. PDF text extraction requires pdftotext (poppler-utils)

The full-text search feature extracts text from uploaded PDFs using the
`pdftotext` system binary (from the `poppler-utils` package). If
`pdftotext` is not installed, search will only find documents by their
metadata (title, union name, document type) — NOT by their content.

**What this means for testing:** search works in the dev environment
(`pdftotext` is installed). **What this means for production:** the
production server must have `poppler-utils` installed
(`apt-get install poppler-utils` on Debian/Ubuntu).

---

## 5. The Retention Queue is feature-flagged (off by default)

The Retention Queue (document disposal workflow) is hidden unless the
environment variable `NEXT_PUBLIC_RETENTION_ENABLED=true` is set. This is
because the retention policy (D5) has not been finalized — the Registrar
has not yet decided the exact retention periods.

**What this means for testing:** if you don't see "Retention Queue" in
the nav bar, that's expected. If you want to test it, ask the developer
to set the flag. **What this means for production:** the flag must be set
to `true` before go-live if retention is in scope.

---

## 6. Two-factor authentication (2FA) is optional per user

2FA is supported but not enforced. Each user decides whether to enable it
in their Account Security settings. There is no system-wide "require 2FA"
setting.

**What this means for testing:** you can log in without 2FA (the demo
accounts don't have it enabled). **What this means for production:** the
Registrar should decide whether 2FA is mandatory for staff. If so, a
system-wide enforcement flag needs to be added (currently not built).

---

## 7. Email notifications require SMTP configuration

Email notifications (e.g. "your document was approved", "compliance
digest") are sent via SMTP. If SMTP is not configured (no
`SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` in `.env`), emails
will silently fail — the system will log an error but not crash.

**What this means for testing:** you may not receive email notifications
during testing (SMTP may not be configured in the dev environment). The
in-app notification bell (top-right) will still work. **What this means
for production:** SMTP must be configured before go-live.

---

## 8. SMS and WhatsApp notifications are opt-in and require Twilio

SMS and WhatsApp notifications are supported via Twilio, but are
opt-in per user (default off) and require `TWILIO_ACCOUNT_SID`,
`TWILIO_AUTH_TOKEN`, and `TWILIO_WHATSAPP_FROM` in `.env`.

**What this means for testing:** SMS/WhatsApp will not work unless Twilio
is configured. This is expected. **What this means for production:**
configure Twilio if SMS/WhatsApp notifications are in scope.

---

## 9. Cron jobs require manual setup + CRON_SECRET

The system has 6 cron endpoints (compliance snapshot, compliance sweep,
compliance digest, audit retention sweep, etc.) that must be called
periodically. They are NOT automatically scheduled — you must set up an
external scheduler (e.g. a system cron job, a Kubernetes CronJob, or a
service like cron-job.org) to hit these endpoints with the
`CRON_SECRET` bearer token.

**What this means for testing:** the compliance trend chart may show "no
data yet" if no cron has run. The dashboard still works — it fetches live
data. **What this means for production:** schedule the cron endpoints
before go-live. See the cron documentation in the codebase
(`src/app/api/cron/`).

---

## 10. File upload limit is 50 MB

Document uploads are capped at 50 MB per file. Files larger than this
will be rejected with a clear error message.

**What this means for testing:** upload a small PDF (under 50 MB) to test
the flow. **What this means for production:** if unions need to upload
larger documents (e.g. high-resolution scanned returns), the limit can be
raised in `src/app/api/unions/[unionId]/documents/route.ts`.

---

## 11. Public rate limiting is partial (D14)

Some public API routes (`/api/public/unions`, `/api/public/files/[id]`)
are rate-limited. Others (`/api/public/unions/[id]`, `/api/public/stats`)
are NOT rate-limited yet (D14 is deferred).

**What this means for testing:** no visible impact. **What this means for
production:** before go-live, rate limiting should be applied to all
public routes to prevent abuse.

---

## 12. The compliance rate rule is provisional (D1)

The compliance rate formula (COMPLIANT / (COMPLIANT + EXPIRING + OVERDUE
+ AWAITING_REVIEW + MISSING)) was confirmed by the Registrar on
2026-10-06 but marked "provisional, not final." Awaiting Review documents
count toward the denominator (not the numerator) — this means a union
that has filed on time can show as non-compliant until the Registrar
reviews.

**What this means for testing:** if the compliance rate looks lower than
expected, check whether there are Awaiting Review documents in the queue.
**What this means for production:** the formula may change. It lives in
ONE place (`computeRateFromCounts` in `src/lib/dashboard/metrics.ts`) so
a change is a single-function edit.

---

## 13. Officers with no assigned union see nothing (D17)

If an Officer account has no `assignedUnionId`, they see NO data (a plain
"Forbidden" response) — not all data. This is intentional (fail-closed)
but can be confusing if an Officer is created without an assignment.

**What this means for testing:** if you create a new Officer account,
assign them to a union immediately — otherwise they'll see nothing. The
demo Officer (`officer@example.com`) is assigned to Papua Maritime
Workers Union.

---

## 14. The public compliance rate endpoint exists but is not displayed

`GET /api/public/stats` returns the overall compliance rate without
authentication. No public page displays it. The Registrar has not decided
whether the public should see a rate at all (D2 is open).

**What this means for testing:** you won't see a compliance rate on the
public portal. That's intentional. **What this means for production:** D2
must be decided before go-live (either display the rate on the public
portal, or remove it from the API response).

---

## 15. The "Representative" role no longer exists (D7)

The system previously had a `REPRESENTATIVE` role (for union
representatives accessing a self-service portal). This was removed in D7.
The only roles are now `REGISTRAR`, `INSPECTOR`, and `OFFICER`.

**What this means for testing:** if you see references to "Representative"
or "/portal" in old documentation, ignore them — they're historical. The
officer role covers union-side access. **What this means for production:**
no action — the removal is complete.

---

## 16. Some usability gaps are known (Phase 2/3 work)

A usability audit found 14 confirmed gaps (see
`docs/usability-gap-register.md`). The most visible to stakeholders:
- 12 forms use toast-only validation (no inline error messages next to
  the field). Errors appear as a toast at the bottom of the screen.
- 8 places use the browser's native `confirm()` dialog instead of a
  styled confirmation dialog (less polished but functional).
- The dashboard's "Awaiting Review" KPI tile links to the compliance
  matrix (filtered), not to the Review Queue. This is a known UX issue.

**What this means for testing:** these are known issues — don't file
them as new bugs. They're tracked in the usability gap register for
Phase 2/3 remediation.
