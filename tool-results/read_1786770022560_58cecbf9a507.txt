   136→                   Enable 2FA on your account                                                                               3 min
   137→
   138→
   139→
   140→
   141→          Two-factor authentication uses TOTP (RFC 6238) — the same standard as Google Authenticator, Authy,
   142→          1Password. Setup happens in two phases: first you scan the QR code and verify a real code (only then is
   143→          the secret persisted), then every future login requires both password and a fresh 6-digit code. Disabling
   144→          2FA requires your password; an admin can reset it (which also clears the secret).
   145→
   146→          TRY IT
   147→          1. Sign in as registrar@example.com.
   148→          2. Open the user menu (top-right) → "Account Security".
   149→          3. Click "Enable 2FA" → scan the QR code with an authenticator app.
   150→          4. Enter the 6-digit code from your app to confirm.
   151→          5. Sign out, then sign back in — you'll be prompted for a 2FA code after your password.
   152→
   153→              WHAT TO LOOK FOR
   154→
   155→          → The QR code is generated server-side from a per-user secret stored in the DB; the secret is never sent back to the
   156→              client in plaintext after setup.
   157→
   158→          → After enabling, the login flow has TWO steps: password → 2FA challenge → authenticated session. The 2FA challenge
   159→              is a short-lived opaque token (30s), not the session itself.
   160→
   161→          → A wrong 2FA code increments the SAME lockout counter as a wrong password — 3 wrong attempts of any kind locks
   162→              the account.

   212→                   Upload a document with version history                                                                       4 min
   213→
   214→
   215→
   216→
   217→          Documents are filed against a union, typed as one of 13 canonical types (constitution, bylaws, annual
   218→          return, etc.), and stored as files on disk under /storage/unions/{unionId}/{documentId}.bin. SHA-256
   219→          checksums detect duplicates. Uploading a new version of an existing document preserves the old
   220→          version in a version chain — restoring an old version creates a NEW version (v4 with v1's content), never
   221→          mutates history.
   222→
   223→          TRY IT
   224→
   225→          1. Sign in as registrar@example.com.
   226→          2. Open any union (e.g. Papua Maritime).
   227→          3. Scroll to a document-type tile → click "Upload".
   228→          4. Pick a PDF file, give it a title, submit.
   229→          5. After upload, click the document title → "Version history" to see v1.
   230→          6. Upload another file to the same type — note the version number increments.
   231→
   232→              WHAT TO LOOK FOR
   233→
   234→          → The upload is atomic: file written to .tmp first, then renamed — a crash mid-write never produces a partial file.
   235→
   236→          → The checksum is shown in the document detail panel — uploading the same file again to the same union + type
   237→              triggers a duplicate-detection warning.
   238→
   239→          → Version history shows every version with its uploader, timestamp, and file size. Restoring v1 of a v3 doc creates v4
   240→              (with v1's content) — the original v1 row is never mutated.

   264→          The Compliance screen shows every union × every document type in a single matrix. Statuses are
   265→          computed live via pure functions (no DB caching) — so editing a rule instantly changes every union's
   266→          score. The 5 statuses: Compliant (green), Expiring (yellow, ≤90 days to renewal), Overdue (red), Missing

   444→                   Dispose of an expired document                                                                                   4 min
   445→
   446→
   447→
   448→
   449→          Retention is the most irreversible action in the system — once a document is marked disposed, it
   450→          cannot be brought back (the row stays for audit, but it's gone from every active view). The flow:
   451→          pending-disposal list shows documents past their retention period → Approve requires a two-step
   452→          confirmation (type the document title exactly) → Reject snoozes for 30 days. Race-safe: if two Registrars
   453→          click Approve simultaneously, only one succeeds.

   456→          1. Sign in as registrar@example.com.
   457→          2. Click "Retention" in the sidebar.
   458→          3. Note the pending-disposal list — these are docs whose filedAt + retentionYrs ≤ today.
   459→          4. Scroll to the "Retention Schedule" table at the bottom — see retentionYrs per type (constitution = 99 = never
   460→             dispose).
   461→          5. Click "Approve" on any pending doc → the dialog requires you to TYPE THE EXACT TITLE to enable Confirm.
   462→          6. Type the title → click "Confirm Disposal" → the doc disappears from the list.
   463→          7. Open Audit Log → filter by Entity Type = "Retention" → see the disposal entry with severity = Critical.
