    18→## Discrepancy #1: Documents KPI (23) vs Documents-by-Type subtitle (21)
    19→
    20→### Root cause: **different definitions, not a data bug**
    21→
    22→The two numbers use **different filter predicates** on the same `Document` table:
    23→
    24→| Endpoint | Query | Count |
    25→|----------|-------|-------|
    26→| `GET /api/dashboard/stats` (line 44) | `db.document.count({ where: {} })` — no filter | **23** |
    27→| `GET /api/dashboard/document-types` (line 22) | `db.document.findMany({ where: { disposedAt: null } })` then `.length` | **21** |
    28→
    29→The 2-document gap = disposed documents. Verified via DB query:
    30→
    31→```
    32→Total documents (stats route — no disposedAt filter):    23
    33→Non-disposed documents (document-types route):           21
    34→Disposed documents:                                       2
    35→Discrepancy:                                              2  ← matches 23 - 21
    36→```
    37→
    38→### Why this is confusing to users
    39→
    40→The dashboard shows **two different document counts simultaneously**:
    41→- The "Documents" stat card (top row, KPI band) shows **23** — counts everything, including disposed docs
    42→- The "Documents by Type" card subtitle shows **21** — counts only non-disposed docs
    43→
    44→A user looking at both at the same time sees "23 documents" in one place and "21 documents" in another and reasonably wonders which is correct. Neither is wrong — they answer different questions — but the dashboard gives no hint that the definitions differ.
    45→
    46→### Which definition is "correct"?
    47→
    48→That's a product decision for chunk 1.1. Two reasonable options:
    49→- **Option A (consistency):** Both endpoints use the same filter. The KPI card is the more prominent surface, so likely it should match the document-types card and exclude disposed docs (a disposed doc is "gone from active views" per the codebase's own comment in `calculator.ts:252`).
    50→- **Option B (clarity):** Keep both numbers but relabel them — "23 Documents (all)" vs "21 Active documents (non-disposed)" — so the distinction is explicit.
    51→
    52→Either way, the current state (same label "documents", two different counts, no explanation) is the bug.

    63→## Discrepancy #2: Compliance tiles sum to 78
    64→
    65→### Root cause: **matrix dimensions, not a bug** — 6 unions × 13 required rules = 78 cells
    66→
    67→The 4 compliance tiles (Compliant / Expiring / Overdue / Missing) tally cells from the compliance matrix. The matrix has one cell per **(union × required compliance rule)** pair. Verified via DB query:
    68→
    69→```
    70→Total unions:                       6
    71→Total compliance rules:            13
    72→Required rules (required: true):   13  ← all 13 rules are required
    73→Matrix dimensions:                 6 × 13 = 78 cells
    74→```
    75→
    76→The compliance matrix's cell tally (from `/api/dashboard/stats` → `buildComplianceMatrix`):
    77→
    78→```
    79→COMPLIANT:      17
    80→EXPIRING:        2
    81→OVERDUE:         2
    82→MISSING:        57
    83→NOT_APPLICABLE:  0
    84→───────────────────
    85→Total cells:    78  ← matches 6 × 13
    86→```
    87→
    88→Sum of the 4 tiles shown in the dashboard (excluding NOT_APPLICABLE which is 0 here): 17 + 2 + 2 + 57 = **78**. ✅
    89→
    90→### Why all 13 rules count toward the matrix (none are NOT_APPLICABLE)
    91→
    92→The `calculateStatus` function in `src/lib/compliance/calculator.ts:246-248` returns `NOT_APPLICABLE` only when `!rule.required`. Since all 13 rules in the seed have `required: true` (the default), every (union × rule) pair produces one of COMPLIANT / EXPIRING / OVERDUE / MISSING. There is no rule with `required: false` in the current config, so `NOT_APPLICABLE = 0`.
    93→
    94→This is **not a bug** — it's the intended design. The matrix is supposed to cover every (union × required-rule) pair. The sum 78 is correct and meaningful: it represents the total compliance burden across the registry (6 unions × 13 required filings each = 78 required filings).
    95→
    96→### Caveat: the chunk prompt's "14" vs the live "17"
    97→
    98→The chunk prompt says "Compliant (14, green)" but the live DB shows 17 compliant cells. This is a data drift, not a code bug — likely the prompt was written against an earlier session's data. The audit is against live data (2026-09-02 01:55 UTC backup), which has 17. Chunk 1.1 should not "fix" 17 → 14; the live data is authoritative.
    99→
   100→### Why "Missing" is so high (57 of 78 = 73%)
   101→
   102→This is also not a bug — it's the review workflow's interaction with the compliance calculator. From chunk "Step 4" of the prior session:
   103→
   104→> Review workflow (Option A): an un-reviewed upload doesn't count toward compliance. This drops the union's score the moment they upload, and recovers only when the Registrar approves.
   105→
   106→`src/lib/compliance/calculator.ts:264-266` returns `MISSING` whenever `document.reviewStatus !== "APPROVED"`. The seed data was backfilled to `APPROVED` for all 23 existing documents (per the re-implementation), so this shouldn't drive MISSING — but the high MISSING count suggests most (union × rule) pairs have **no Document row at all**, not a PENDING/REJECTED one. Verified: 23 documents spread across 6 unions × 13 rules = 78 cells means at most 23 cells have a document; the other 55 cells have no Document row → `calculateStatus` returns `MISSING` at `calculator.ts:256`. Plus 2 disposed docs → also MISSING. So 57 = (78 - 23) + 2 = 57. ✅

   876→## Appendix — Chunk 4.1 Handoff (KPI drill-through with deep-linkable status filters)
   877→
   878→### Helper mechanism finding
   879→
   880→The 1.3 filter helper `navigateToComplianceFilter(status)` was **in-memory state-based**: it returned `{ view: "compliance", filter: status }`, and `page.tsx` called `setInitialStatusFilter()` and `setActiveView()` — both React `useState`. **No URL params were involved — deep links were broken.**
   881→
   882→**Mechanism upgraded in this chunk**: `page.tsx` now reads `?view=` and `?status=` from URL params on mount (alongside the existing `?token=`, `?login=`, `?union=` params). The filter helper's API (`navigateToComplianceFilter`) is unchanged — it still returns `{ view, filter }`. The change is in `page.tsx`'s `useEffect` which now parses URL params via the new `parseStatusParam()` and `parseViewParam()` functions from the links module. The helper's unit tests (8 tests) still pass unchanged.
   883→
   884→### Param contract (public API for future chunks)
   885→
   886→```ts
   887→// src/lib/dashboard/dashboard-links.ts
   888→export const PARAM_VIEW = "view";
   889→export const PARAM_STATUS = "status";
   890→
   891→// URL builders:
   892→complianceFilterUrl("OVERDUE")  → "/?view=compliance&status=OVERDUE"
   893→complianceUnfilteredUrl()       → "/?view=compliance"
   894→unionsListUrl()                  → "/?view=unions"
   895→
   896→// Param parsers (validate + degrade to null):
   897→parseStatusParam("OVERDUE")     → "OVERDUE"
   898→parseStatusParam("bogus")       → null  (degrade to unfiltered)
   899→parseStatusParam(null)           → null  (absent → unfiltered)
   900→parseViewParam("compliance")    → "compliance"
   901→parseViewParam(null)             → null  (absent → dashboard)
   902→```
   903→
   904→Values are uppercase `ComplianceStatus` values from `status-config.ts` — no literal strings. Future chunks can add `?daysAhead=`, `?documentType=`, `?status=overdue,expiring` by extending the links module without breaking existing URLs.
