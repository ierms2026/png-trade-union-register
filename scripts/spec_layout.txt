                   Enable 2FA on your account                                                                               3 min




          Two-factor authentication uses TOTP (RFC 6238) — the same standard as Google Authenticator, Authy,
          1Password. Setup happens in two phases: first you scan the QR code and verify a real code (only then is
          the secret persisted), then every future login requires both password and a fresh 6-digit code. Disabling
          2FA requires your password; an admin can reset it (which also clears the secret).

          TRY IT
          1. Sign in as registrar@example.com.
          2. Open the user menu (top-right) → "Account Security".
          3. Click "Enable 2FA" → scan the QR code with an authenticator app.
          4. Enter the 6-digit code from your app to confirm.
          5. Sign out, then sign back in — you'll be prompted for a 2FA code after your password.

              WHAT TO LOOK FOR

          → The QR code is generated server-side from a per-user secret stored in the DB; the secret is never sent back to the
              client in plaintext after setup.

          → After enabling, the login flow has TWO steps: password → 2FA challenge → authenticated session. The 2FA challenge
              is a short-lived opaque token (30s), not the session itself.

          → A wrong 2FA code increments the SAME lockout counter as a wrong password — 3 wrong attempts of any kind locks
              the account.

                   Upload a document with version history                                                                       4 min




          Documents are filed against a union, typed as one of 13 canonical types (constitution, bylaws, annual
          return, etc.), and stored as files on disk under /storage/unions/{unionId}/{documentId}.bin. SHA-256
          checksums detect duplicates. Uploading a new version of an existing document preserves the old
          version in a version chain — restoring an old version creates a NEW version (v4 with v1's content), never
          mutates history.

          TRY IT

          1. Sign in as registrar@example.com.
          2. Open any union (e.g. Papua Maritime).
          3. Scroll to a document-type tile → click "Upload".
          4. Pick a PDF file, give it a title, submit.
          5. After upload, click the document title → "Version history" to see v1.
          6. Upload another file to the same type — note the version number increments.

              WHAT TO LOOK FOR

          → The upload is atomic: file written to .tmp first, then renamed — a crash mid-write never produces a partial file.

          → The checksum is shown in the document detail panel — uploading the same file again to the same union + type
              triggers a duplicate-detection warning.

          → Version history shows every version with its uploader, timestamp, and file size. Restoring v1 of a v3 doc creates v4
              (with v1's content) — the original v1 row is never mutated.

     C. Compliance
     The highest-leverage principle of Phase 3: compute live, never store. Every status is recomputed on read.




                   Review compliance across all unions                                                                        3 min




          The Compliance screen shows every union × every document type in a single matrix. Statuses are
          computed live via pure functions (no DB caching) — so editing a rule instantly changes every union's
          score. The 5 statuses: Compliant (green), Expiring (yellow, ≤90 days to renewal), Overdue (red), Missing
          (gray), Not Applicable (excluded from scoring).

          TRY IT

          1. Sign in as registrar@example.com.
          2. Click "Compliance" in the sidebar.
          3. Note the matrix: rows = unions, columns = document types, cells = colored status badges.
          4. Click any cell to deep-link into that union's detail page.
          5. Use the "Status" filter dropdown to show only Overdue unions.

              WHAT TO LOOK FOR

          → The overall score per union = (Compliant types) / (required types) × 100. Not-Applicable types are excluded from
              BOTH numerator and denominator.

          → The "Expiring" status uses the EXPIRING_WINDOW_DAYS constant (90 days) — change the constant in
              src/lib/auth/constants.ts and every status recomputes immediately.

          → Officer signing in sees the same screen but scoped to only their assigned union — server-side filter, not client-side.

                   Dispose of an expired document                                                                                   4 min




          Retention is the most irreversible action in the system — once a document is marked disposed, it
          cannot be brought back (the row stays for audit, but it's gone from every active view). The flow:
          pending-disposal list shows documents past their retention period → Approve requires a two-step
          confirmation (type the document title exactly) → Reject snoozes for 30 days. Race-safe: if two Registrars
          click Approve simultaneously, only one succeeds.

          TRY IT
          1. Sign in as registrar@example.com.
          2. Click "Retention" in the sidebar.
          3. Note the pending-disposal list — these are docs whose filedAt + retentionYrs ≤ today.
          4. Scroll to the "Retention Schedule" table at the bottom — see retentionYrs per type (constitution = 99 = never
             dispose).
          5. Click "Approve" on any pending doc → the dialog requires you to TYPE THE EXACT TITLE to enable Confirm.
          6. Type the title → click "Confirm Disposal" → the doc disappears from the list.
          7. Open Audit Log → filter by Entity Type = "Retention" → see the disposal entry with severity = Critical.

              WHAT TO LOOK FOR

          → The two-step confirm: the Confirm Disposal button is disabled until titleInput.trim() === entry.title.trim(). This is the
              same pattern GitHub uses for repo deletion.

          → The audit entry is severity = Critical (disposal is irreversible) — retention_reject is severity = Info (snooze is reversible).

          → The race-safe updateMany pattern: if you open two browser tabs and click Approve on the same doc in both, only

          The notification bell has existed since Phase 1 but nothing populated it until Phase 6's BJS-01 daily
